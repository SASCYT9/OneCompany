# Системний аудит пошуку каталогу OneCompany

Дата: 30 вересня 2026 року. Обсяг: загальний каталог усіх брендів, пошук, селектори автомобілів, категорії, авто і мото, поєднання фільтрів та публікація даних.

Виявлені проблеми стосуються архітектури каталогу та якості вихідної сумісності. У цій роботі підготовлено локальні виправлення спільного запиту, селекторів, категоризації та стану карток. Зміни перевірено на окремій тимчасовій базі. Production-код, дані, прапорці та кеші не змінювалися.

## Результати публічної перевірки

Виконано 550 запитів лише читанням: 27 брендів, 50 значень марки та 426 пар марки і моделі. Окремо перевірено запити з кількома брендами.

| Перевірка | Результат до виправлень |
| --- | --- |
| Вибір BMW M3 G80 | 169 товарів |
| Текст BMW M3 G80 | 134 товари |
| BMW M3 G80 та Eventuri | 6 товарів |
| BMW M3 G80 та CSF | 8 товарів |
| BMW M3 G80 та Eventuri і CSF | 0 товарів |
| Марка Skoda | 175 товарів |
| Марка Škoda | 0 товарів |
| Каталог з `scope=auto` | 17 764 товари |
| Каталог без режиму | 17 764 товари |
| Мотоциклетний каталог | 368 товарів |
| Селектор мотоциклетних марок | HTTP 503 |

У 20 з 27 брендів немає видимих груп товарів. Ці бренди містять 14 843 товари. Ще 28 позицій Fi EXHAUST не входять у видимі групи. Разом 14 871 з 17 764 позицій перевіреного запиту не представлені в категоріях. Цей запит помилково включав мотоциклетні товари до авто, тому його кількість не є окремим підтвердженим розміром автомобільного асортименту.

121 з 426 запитів моделі не повернув кузовів. Це не означає 121 помилку даних: серед причин є штучне додавання моделей із загального словника. Кожний такий випадок потребує зіставлення з фактичними застосуваннями.

Докази: `catalog-architecture-public-audit.json`, `catalog-architecture-public-summary.json`, `multibrand-vehicle-audit.json` і `brand-category-coverage.csv` у `One Company 2/outputs/catalog-filter-audit-2026-09-30/`.

## Причини та підготовлені виправлення

| Причина | Зміна | Межа результату |
| --- | --- | --- |
| Кілька брендів перемикали запит із проєкції на інший читач | Додано об'єднання брендів у SQL, ORM, фасетах і адаптері; прибрано цей привід переходу на резервний шлях | Інші непідтримані виміри ще мають окремий gate |
| Текст авто повторно вимагався у назві або індексі вже сумісного товару | Один план виділяє авто та залишкові слова товару для пошуку й підказок | Конфлікт із явно вибраним авто та неоднозначні назви залишаються текстовими |
| `auto` перетворювався на відсутність обмеження | Збережено режим у API та SSR; авто виключає явно мотоциклетні записи | Історичний `SHOP` зберігається в авто до нормалізації; невизначені джерела потребують аудиту |
| Cupra/CUPRA та Skoda/Škoda мали різні ідентичності | Додано спільні канонічні назви й aliases | Не об'єднуються різні комплектації лише через схожість назв |
| Селектор додавав моделі та кузови із загального мовного словника | Прибрано додавання непідтверджених варіантів; нормалізуються фактичні значення джерела | Відсутні підтверджені застосування потрібно імпортувати, а не замінювати словником |
| Ключ кешу не містив бренд, хоча BMC змінював набір кандидатів | Ключ враховує нормалізовану множину брендів | TTL кешу та міжпроцесне оновлення залишаються окремим завданням |
| Записи CHASSIS губилися при виборі кузова через GENERATION | Підтримано точний CHASSIS у запиті, фасетах і перехідному читачі | UNKNOWN не перетворюється на wildcard |
| Стара політика могла зіставлятися з новою проєкцією | Зв'язано версії політики й проєкції, включно з матеріалізованими ціновими фасетами | Потрібне завершення публікації поточних канонічних записів |
| Без зв'язку з категорією проєкція втрачала класифікацію | Збережено чинну загальну таксономію у похідних даних; назва бренду не переважає назву самого виробу | Поточні проєкції потребують керованого оновлення та перевірки класифікації |
| Позначка сумісності з'являлася на старих картках під час нового запиту | Позначка не показується під час завантаження або помилки | Перевірка достовірності вихідної сумісності залишається обов'язковою |
| Кнопка другого бренду прибирала перший; видалення одного чипа очищало всі бренди | Додано справжнє додавання і вилучення окремих брендів; збережено поточний вигляд | URL та API використовують те саме об'єднання |
| Глобальне правило переписувало Audi RS5 B9 на B8 через особливість KW | Вибраний кузов зберігається; особливі типові коди мають нормалізуватися на вході конкретного джерела | KW-записи потребують окремого узгодження типових кодів перед випуском |
| Відкриті діапазони років могли ставати одним роком, а рік — кузовом | do88, Burger і GiroDisc використовують спільний парсер років; роки не стають кодами кузова GiroDisc | Для виправлення старих даних потрібна нова версія мапування та повторна публікація |

Під час SQL-перевірки знайдено й виправлено регресію: після додавання перевірки версії матеріалізований набір цінових фасетів також повинен зберігати `sourceVersion`. Додано перевірку ціни разом з авто та кількома брендами.

## Підтвердження на тимчасовій базі

Створено ізольований PostgreSQL через PGlite 0.5.8 та PGlite Socket 0.2.11. Виконано всі 47 SQL-міграцій репозиторію з потрібними розширеннями. Клієнт — Prisma 6.19.3. База містить явно позначені тестові записи, а не копію production.

Інтеграційний тест перевіряє об'єднання брендів, авто і мото, записи лише з CHASSIS, UNKNOWN двигуна, неправильний кузов, рік, ціновий фільтр та стару версію політики. Він пройшов без пропусків.

Локальний HTTP API підтвердив:

| Запит | Очікування і результат |
| --- | --- |
| Текст BMW M3 G80 | 2 сумісні тестові товари, хоча назви не містять авто |
| Той самий текст та максимум 15 EUR | 1 товар за 10 EUR |
| Два бренди та BMW M3 G80 | 2 товари |
| Мото | 1 мотоциклетний товар |
| BMW M3 та неправильний F80 | 0 товарів |

У Chrome перевірено каскад BMW → M3 → G80, два вибрані бренди та видалення одного чипа зі збереженням авто й іншого бренду. Збережено знімок `local-catalog-multibrand-bmw-m3-g80.png`. Тестові товари позначено в їхніх назвах. Під час завантаження старі картки не отримують нової позначки сумісності.

PGlite підтверджує правильність SQL на PostgreSQL, але не замінює вимірювання навантаження, конкуренції та поведінки production PostgreSQL. У цій сесії Docker Desktop був запущений, але запити CLI до його сервера завершувалися таймаутом. Його служби й контейнери не перезапускалися.

## Проблеми даних, які ще відкриті

Підсумкові локальні перевірки коду: 554 з 554 тестів каталогу, TypeScript без помилок,
lint змінених файлів — 0 помилок і 5 попереджень. Попередній запуск усього проєктного
unit-набору мав 1 603 тести, з них 1 587 успішних і 16 невдалих. Дві перевірки
каталогу з цього списку оновлено відповідно до нового контракту й включено до
успішного цільового набору. Повний проєктний набір після всіх правок не оголошується
успішним; решту відмов потрібно окремо розібрати.

У знімку do88 від 30 вересня є 1 090 відповідних товарів. Діагностика початкового адаптера дала 610 універсальних записів, 412 записів для авто та 68 записів для перевірки. Ці статуси початкового адаптера не є доказом правильності опублікованих політик.

Для LF-270 адаптер видаляє дужки з `BMW G80 G87, S58 (M2 M3 M4)` і утворює модель `G80 G87, S58`. Це не правильна модель M3. У знімку знайдено 137 записів для перегляду за евристикою змішування моделі, платформи та двигуна. Число 137 не є числом підтверджених помилок: наприклад, S80 може бути правильною моделлю Volvo.

Такі записи треба зіставити з офіційною сумісністю за SKU та варіантом і записати окремі пов'язані застосування. Не можна механічно створювати всі комбінації моделей і кузовів із назви. Подібна перевірка потрібна кожному джерелу, а не лише do88.

Моторежим ще потребує повного підтвердженого набору застосувань у production. Селектори ще не враховують усю поточну комбінацію товарних фільтрів. Product type, product kind, strict та глобальні фасети досі можуть використовувати інший читач. Їхні контракти потрібно узгодити після заповнення проєкцій, не перетворюючи непідтриманий параметр на ігнорований.

## Наступні умови випуску

1. Перевірити та виправити джерела сумісності за всіма брендами; зберегти походження кожного факту й список нерозв'язаних записів.
2. Підготувати dry-run нових ревізій і проєкцій з правильними категоріями, роками та сумісністю, збереженням SKU та всіх ID. Старі незмінні ревізії не редагуються.
3. Узгодити типові коди KW та інші aliases на рівні джерела. Зміна запиту не є виправленням цих даних.
4. Перевірити однакові результати всіх активних читачів і селекторів, включно з товарними фільтрами, UA/EN та mobile.
5. Завершити перевірку продуктивності та публікації. Підготувати окремі зміни коду й даних, відкат та контроль черги публікації.
6. Після дозволеного випуску повторити повну публічну матрицю. Локальні тести та успішний deploy окремо не доводять повноту каталогу.
